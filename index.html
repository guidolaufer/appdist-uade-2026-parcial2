Checklist de entrega
💡
El examen tiene código con antipatrones intencionales. Tu trabajo: identificarlos, nombrarlos, y explicar cómo se arreglan.
Kotlin / Android
🔴 God Activity
Cómo se ve: una Activity con 300+ líneas, lógica de negocio, acceso a BD, llamadas de red y UI mezcladas.
Por qué es malo: imposible de testear, mantener o reusar. Viola el Principio de Responsabilidad Única (SRP).
Cómo se arregla: extraer lógica a ViewModel, acceso a datos a un Repository, dejar la Activity solo con código de UI.
🔴 Red / BD en el hilo principal (Main Thread)
Cómo se ve: OkHttp, Volley, o db.query() llamados directamente en onCreate o en un click handler sin coroutine.
Por qué es malo: bloquea el UI thread. Si tarda más de 5 segundos, Android lanza ANR (App Not Responding). Desde Android 3.0, las llamadas de red en main thread crashean directamente.
Cómo se arregla: viewModelScope.launch(Dispatchers.IO) { ... } o suspend fun en Room.
🔴 Sensor / Listener sin desregistrar
Cómo se ve: sensorManager.registerListener(this, sensor, ...) en onCreate pero sin unregisterListener en onPause o onDestroy.
Por qué es malo: memory leak. El sensor mantiene una referencia a la Activity, que no puede ser recolectada por el GC aunque la Activity esté destruida. Además consume batería innecesariamente.
Cómo se arregla: desregistrar en onPause().
🔴 Magic numbers / strings
Cómo se ve: if (battery < 20), val url = "http://192.168.1.1/api" esparcidos en el código.
Por qué es malo: semántica perdida, difícil de mantener. Si el valor cambia, hay que buscarlo en todo el código.
Cómo se arregla: extraer a companion object con const val BATTERY_LOW_THRESHOLD = 20.
🔴 Hardcoded credentials / URLs
Cómo se ve: val apiKey = "sk-abc123" o URL de producción en el código fuente.
Por qué es malo: riesgo de seguridad grave si el repo es público. Las credenciales quedan en el historial de git.
Cómo se arregla: usar BuildConfig con variables en local.properties (que va en .gitignore), o variables de entorno.
React
🔴 Fat Component (God Component)
Cómo se ve: un componente de 250+ líneas con useEffect de red, lógica de negocio, manejo de formularios y render todo junto.
Por qué es malo: mismo problema que God Activity. Imposible de reusar o testear.
Cómo se arregla: extraer lógica a custom hooks (usePatients()), extraer secciones del render a subcomponentes.
🔴 Fetch directo en componente
Cómo se ve: fetch('/api/data') o axios.get(...) dentro de useEffect directamente en el componente, no en un servicio.
Por qué es malo: lógica de datos acoplada a la UI. Si la API cambia, hay que buscar en todos los componentes.
Cómo se arregla: extraer a un custom hook useData() o a un archivo services/api.ts.
🔴 useEffect sin cleanup
Cómo se ve: useEffect que abre una suscripción, setea un intervalo o agrega un event listener, pero no retorna una función de limpieza.
Por qué es malo: memory leak. La suscripción/intervalo sigue activa después de que el componente se desmonta. Puede causar "setState on unmounted component".
Cómo se arregla: return () => { subscription.unsubscribe(); clearInterval(id); }.
🔴 Key ausente o incorrecta en listas
Cómo se ve: items.map(item => <Item />) sin key, o key={index}.
Por qué es malo: React no puede identificar qué elemento cambió, lo que causa re-renders incorrectos y bugs de estado.
Cómo se arregla: key={item.id} con un identificador único y estable.
🔴 Prop drilling excesivo
Cómo se ve: un prop pasado por 3+ niveles de componentes solo para que el último hijo lo use.
Por qué es malo: todos los componentes intermedios quedan acoplados. Un cambio de tipo o nombre obliga a tocar múltiples archivos.
Cómo se arregla: Context de React, Zustand, o Redux para estado global.
MVVM — Model View ViewModel

Patrón de arquitectura estándar en Android moderno (y usado en React con custom hooks).

┌─────────────────────────────────────────────────────┐ │ UI LAYER │ │ Activity / Fragment / Composable / Componente React│ │ Solo: renderizar estado, capturar eventos de UI │ └──────────────┬──────────────────────────────────────┘ │ observa LiveData / StateFlow / useState ▼ ┌─────────────────────────────────────────────────────┐ │ VIEWMODEL / CUSTOM HOOK │ │ Lógica de presentación, transformación de datos │ │ Sobrevive rotaciones (Android). NO tiene ref a UI │ └──────────────┬──────────────────────────────────────┘ │ llama funciones ▼ ┌─────────────────────────────────────────────────────┐ │ REPOSITORY │ │ Abstrae el origen de los datos. │ │ El ViewModel NO sabe si vienen de red o de caché │ └───────┬────────────────────────┬────────────────────┘ │ │ ▼ ▼ ┌───────────────┐ ┌─────────────────────┐ │ API remota │ │ Base de datos local │ │ (Retrofit/ │ │ (Room / SQLite) │ │ Axios) │ │ │ └───────────────┘ └─────────────────────┘
✅ ¿Por qué MVVM?
Testeable: podés testear el ViewModel sin UI.
Sobrevive rotaciones: el ViewModel no se destruye al rotar (Android).
Separación de responsabilidades: cada capa tiene una sola responsabilidad.
Repository Pattern

El Repository es la única fuente de verdad para los datos. Decide si traer de red o de caché local.

// Repository — abstrae el origen class PatientRepository( private val api: PatientApi, private val db: PatientDao ) { suspend fun getPatients(): List<Patient> { return try { val remote = api.fetchPatients() db.insertAll(remote) // cachear en local remote } catch (e: Exception) { db.getAll() // fallback a local } } }

Coroutines — operaciones asíncronas
❌ MAL — red en main thread
override fun onCreate(...) { // CRASH en Android moderno val data = api.getData() updateUI(data) }
✅ BIEN — con coroutine
override fun onCreate(...) { viewModel.data.observe(this) { data -> updateUI(data) } } // En el ViewModel: viewModelScope.launch { val data = withContext(Dispatchers.IO) { api.getData() } _data.value = data }

Dispatchers: Dispatchers.Main = UI thread. Dispatchers.IO = red y disco. Dispatchers.Default = CPU intensivo.

Room — BD local correcta
// 1. Entity (tabla) @Entity(tableName = "patients") data class Patient( @PrimaryKey val id: Int, val name: String, val room: String ) // 2. DAO (queries) @Dao interface PatientDao { @Query("SELECT * FROM patients") suspend fun getAll(): List<Patient> // suspend → no puede correr en main thread @Insert(onConflict = OnConflictStrategy.REPLACE) suspend fun insertAll(patients: List<Patient>) } // 3. Database @Database(entities = [Patient::class], version = 1) abstract class AppDatabase : RoomDatabase() { abstract fun patientDao(): PatientDao }
✅ Room vs SQLite directo
Room verifica queries en tiempo de compilación. SQLite directo falla en runtime. Room integra con Flow/LiveData para reactivity automática. Room obliga a que los métodos del DAO sean suspend, forzando ejecución fuera del main thread.

Sensores en Android
❌ MAL — sin desregistrar

class MainActivity : AppCompatActivity(), SensorEventListener { private lateinit var sensorManager: SensorManager private var sensor: Sensor? = null override fun onCreate(...) { sensorManager = getSystemService(...) sensor = sensorManager.getDefaultSensor( Sensor.TYPE_ACCELEROMETER) } override fun onResume() { super.onResume() sensorManager.registerListener( this, sensor, SENSOR_DELAY_NORMAL) } override fun onPause() { super.onPause() sensorManager.unregisterListener(this) } }

🔴 Permiso declarado pero no pedido en runtime
Desde Android 6 (API 23), los permisos "peligrosos" (ubicación, cámara, contactos) deben pedirse en tiempo de ejecución con ActivityCompat.requestPermissions(). Declararlos solo en el Manifest no alcanza. El app crashea o funciona mal silenciosamente.

Ciclo de vida
¿Qué pasa con el ciclo de vida al rotar la pantalla? ▼
La Activity se destruye y se vuelve a crear: onPause → onStop → onDestroy → onCreate → onStart → onResume. Por eso cualquier estado guardado en variables de la Activity se pierde. La solución es usar ViewModel (sobrevive a la rotación) o onSaveInstanceState().
¿Por qué no se debe hacer una llamada de red en onCreate? ▼
onCreate corre en el main thread (UI thread). Las operaciones de red son bloqueantes. Si bloquean el main thread más de 5 segundos, Android lanza un ANR (App Not Responding). Desde Android 3.0, las llamadas de red en main thread lanzaron NetworkOnMainThreadException directamente. La solución: viewModelScope.launch(Dispatchers.IO).
¿Diferencia entre onStop y onDestroy? ▼
onStop: la Activity no es visible pero puede volver (el sistema la puede matar si necesita memoria). onDestroy: la Activity termina definitivamente (usuario presionó Back, llamó finish(), o el sistema la destruyó). Los recursos pesados se liberan en onDestroy; los sensores se liberan en onPause.
¿Qué es un memory leak en el contexto de Android? ▼
Cuando un objeto mantiene una referencia a una Activity/Fragment que ya debería estar destruida, impidiendo que el Garbage Collector la limpie. Causas comunes: sensores no desregistrados, listeners no eliminados, suscripciones no canceladas, o corutinas sin scope apropiado. Resultado: la app consume cada vez más RAM hasta crash.
Arquitectura
¿Por qué usar MVVM en lugar de poner todo en la Activity? ▼
  • Testeable: el ViewModel no depende de Android, se puede testear con JUnit.
  • Sobrevive rotaciones: el ViewModel vive más que la Activity.
  • Separación de responsabilidades: la Activity solo actualiza la UI, el ViewModel maneja la lógica.
  • Mantenible: un cambio en la UI no rompe la lógica y viceversa.
¿Qué es el Repository pattern y por qué usarlo? ▼
El Repository es una capa que abstrae el origen de los datos. El ViewModel no sabe ni le importa si los datos vienen de la red, de caché o de la BD local. Ventajas: podés cambiar de Retrofit a Ktor sin tocar el ViewModel. Podés implementar una lógica de "si no hay red, usá el caché" en un solo lugar.
¿Qué cambiarías de este código y por qué? (God Activity) ▼
Respuesta esperada en el examen:
  • Extraer lógica de negocio a un ViewModel.
  • Extraer acceso a datos a un Repository.
  • Mover queries a un DAO de Room con funciones suspend.
  • La Activity solo debería observar el ViewModel y actualizar la UI.
Enfocate en qué movés y por qué, no en el código exacto.
React
¿Qué es useEffect y cuándo usar el array de dependencias? ▼
useEffect corre después de que React actualiza el DOM (side effects). El array de dependencias controla cuándo se re-ejecuta:
  • Sin array: corre después de cada render.
  • Array vacío []: corre solo al montar el componente.
  • Con valores [id]: corre cuando esos valores cambian.
Siempre retornar cleanup si abrís suscripciones o timers.
¿Por qué usar key en listas y qué pasa si se usa el índice? ▼
React usa key para identificar qué elemento cambió en una lista y hacer el mínimo de cambios en el DOM. Si usás el índice (key={i}), al agregar/eliminar un elemento del principio, todos los índices cambian y React re-renderiza toda la lista innecesariamente — y puede mezclar el estado de los componentes. Usá siempre un id estable y único.
¿Qué es un custom hook y cuándo extraer uno? ▼
Un custom hook es una función que empieza con use y puede llamar a otros hooks. Se extrae cuando: (1) querés reusar lógica con estado entre componentes, (2) un componente tiene demasiada lógica mezclada con el render, o (3) querés testear la lógica por separado de la UI. No genera un nuevo componente en el árbol — solo extrae la lógica.
SQL / Datos
¿Por qué Room es mejor que SQLite directo en Android? ▼
  • Compile-time verification: los errores en las queries se detectan al compilar, no en runtime.
  • Type safety: no hay Cursors manuales ni casteos.
  • Integración reactiva: las queries pueden retornar Flow o LiveData.
  • Fuerza background: los métodos del DAO deben ser suspend, imposible correrlos en main thread accidentalmente.
¿Qué es ANR y cómo se previene? ▼
ANR (App Not Responding): el sistema muestra este error si el main thread no responde por más de 5 segundos. Causas: operación de red, query de BD, o cualquier cómputo pesado en el hilo principal. Se previene ejecutando todo lo que bloquea en Dispatchers.IO con coroutines, y devolviendo los resultados al main thread solo para actualizar la UI.

1. Dos instalaciones con la lista vacía
📱
Contexto del problema
Teléfono A: instalado hoy, nunca recibió respuesta del servidor. Teléfono B: recibió ayer una respuesta exitosa con 0 charlas. Hoy, al abrir sin señal, Room devuelve lista vacía en ambos. ¿Qué mensaje debe ver cada usuario?
🧠 Teoría: Offline-first y estados posibles
💡
Principio offline-first: una app bien diseñada siempre muestra algo útil, incluso sin internet. La diferencia clave es saber por qué la lista está vacía — y eso no se puede saber sin un dato extra persistido.

Hay 3 estados posibles cuando Room devuelve lista vacía:

┌─────────────────────────────────────────────────────────────────┐ │ ROOM DEVUELVE LISTA VACÍA │ ├────────────────┬────────────────┬───────────────────────────────┤ │ lastSyncAt │ Conexión │ Significado │ ├────────────────┼────────────────┼───────────────────────────────┤ │ 0 (nunca) │ sin internet │ Nunca cargó → pedir conexión │ │ fecha ayer │ sin internet │ Datos de ayer → mostrar aviso│ │ 0 (nunca) │ con internet │ Cargando por primera vez... │ └────────────────┴────────────────┴───────────────────────────────┘
a) Mensaje que debería ver cada persona
📱 Teléfono A — lastSyncAt = 0 (nunca sincronizó)
¿Qué sabe la app? Nunca recibió datos del servidor. No puede distinguir "el programa tiene 0 charlas" de "nunca cargué nada". La lista vacía NO es información válida.

Mensaje correcto: "No hay conexión a internet. Conectate para ver el contenido."

¿Por qué no mostrar pantalla vacía? El usuario pensaría que el evento no tiene charlas — lo que es falso. El estado real es: datos desconocidos.
📱 Teléfono B — lastSyncAt = timestamp de ayer
¿Qué sabe la app? Ayer el servidor respondió con 0 charlas (válido en ese momento). Hoy no hay conexión.

Mensaje correcto: "Mostrando contenido del [fecha]. Conectate para ver si hubo cambios."

¿Por qué es distinto al A? Porque la lista vacía ES información válida de ayer. El usuario lo sabe y puede decidir si esperar conexión o no.
b) Dato persistente extra: lastSyncAt
🔑
¿Qué guardar? Un Long con el timestamp (en milisegundos) de la última sincronización exitosa.
¿Dónde? SharedPreferences o una tabla Room con una sola fila (MetaData).
¿Cuándo actualizarlo? Solo cuando el servidor devuelve HTTP 200 y los datos se escribieron en Room correctamente.
// DataStore / SharedPreferences — guardar timestamp suspend fun syncCharlas() { val respuesta = api.getCharlas() // puede fallar db.charlaDao().replaceAll(respuesta) // puede fallar prefs.edit().putLong("lastSyncAt", System.currentTimeMillis()).apply() // ↑ SOLO se llega acá si las dos líneas de arriba no lanzaron excepción } // Al mostrar la lista: val lastSync = prefs.getLong("lastSyncAt", 0L) if (charlas.isEmpty() && lastSync == 0L) { mostrarError("Sin conexión. Conectate para cargar el contenido.") } else if (!isOnline) { mostrarAviso("Datos del ${formatFecha(lastSync)}. Sin conexión.") }
2. Una favorita cambia durante la descarga
⭐
Contexto del problema
Antes de actualizar: charla 11 en Mi agenda, 24 en catálogo sin marcar. Se inicia descarga. Mientras espera, la usuaria agrega la 24 a Mi agenda. La respuesta del servidor trae: retira la 11, mantiene la 24, agrega la 90.
🧠 Teoría: Race condition en datos locales
💡
Race condition = dos operaciones corren "al mismo tiempo" y la que termina segunda pisa a la primera sin saberlo.

En este caso: la descarga del servidor y la acción del usuario sobre favoritas corren en paralelo. El problema aparece cuando el Repository usa el estado de favoritas que leyó al inicio de la descarga, en vez del estado actual al momento de escribir.
LÍNEA DE TIEMPO DEL BUG: t=0 │ Room: charlas = [11★, 24, ...] │ Repository lee favoritas: {11} ← snapshot viejo │ t=1 │ Repository empieza descarga del servidor │ t=2 │ USUARIO marca charla 24 como favorita │ Room.favoritas = {11, 24} ← estado actual │ t=3 │ Servidor responde: [24, 90] │ Repository combina con snapshot {11} ← usa el VIEJO │ Resultado: 24.esFavorita = false ← ¡BUG! pisó la acción del usuario │ 90.esFavorita = false LÍNEA DE TIEMPO CORRECTA: t=3 │ Servidor responde: [24, 90] │ Repository lee favoritas AHORA: {11, 24} ← lee el ACTUAL │ Resultado: 24.esFavorita = true ← correcto │ 90.esFavorita = false
a) Tabla — estado al terminar (correcto)
Charla ¿En catálogo? ¿En Mi agenda? ¿Por qué?
11 No — servidor la retiró No — ya no existe en catálogo La charla 11 dejó de existir. No se puede tener en agenda algo que ya no está en el catálogo.
24 Sí — servidor la mantuvo Sí — usuario la marcó durante descarga La acción del usuario a t=2 debe preservarse. Este es el caso crítico.
90 Sí — servidor la agregó No — nunca fue marcada Charla nueva, el usuario no la conocía. Comienza desmarcada.
b) Acción perdida y cómo evitarlo
🔴 El bug: snapshot de favoritas al inicio de la descarga
Si el Repository hace val favs = db.getIds() antes de llamar a la API y luego usa ese snapshot para combinar con la respuesta, pisa la acción que el usuario realizó mientras esperaba. La charla 24 vuelve a "no marcada" aunque el usuario la marcó.
✅ Solución A: leer favoritas al momento de escribir
Principio: leer el estado de Room lo más tarde posible — justo antes de escribir, cuando ya tenés la respuesta del servidor.
// ❌ MAL — lee favoritas al inicio (snapshot viejo) suspend fun sync() { val favs = db.charlaDao().getFavoritasIds() // lee ANTES de la red val remoto = api.getCharlas() val merged = remoto.map { it.copy(esFavorita = it.id in favs) } db.charlaDao().replaceAll(merged) // pisa acción del usuario } // ✅ BIEN — lee favoritas al momento de escribir suspend fun sync() { val remoto = api.getCharlas() val favs = db.charlaDao().getFavoritasIds() // lee DESPUÉS de la red val merged = remoto.map { it.copy(esFavorita = it.id in favs) } db.charlaDao().replaceAll(merged) }
✅ Solución B (más robusta): tabla separada para favoritas
Usar una tabla Favoritas(charlaId: Int) que el servidor nunca toca. Al actualizar el catálogo se hace replaceAll solo en la tabla de charlas, sin modificar favoritas. Al leer, se hace un JOIN. Así las dos tablas son completamente independientes y no hay posibilidad de race condition.
// Tabla separada — el servidor nunca la toca @Entity data class Favorita(@PrimaryKey val charlaId: Int) // Al sincronizar — solo toca la tabla de charlas suspend fun sync() { val remoto = api.getCharlas() db.charlaDao().replaceAll(remoto) // no toca favoritas } // Al leer — JOIN entre charlas y favoritas @Query("SELECT c.*, (f.charlaId IS NOT NULL) AS esFavorita FROM charlas c LEFT JOIN favoritas f ON c.id = f.charlaId") fun getCharlasConFavoritas(): Flow<List<CharlaConFavorita>>
3. Volver a una ficha y a una lista filtrada
🔙
Contexto del problema
Elegís Día 2 y tema Datos, abrís el detalle de una charla, rotás el teléfono, enviás la app al fondo. Android mata el proceso para liberar memoria. Volvés desde Recientes. ¿Qué pantalla aparece? ¿Los filtros se mantienen al tocar Volver?
🧠 Teoría: Muerte del proceso y back stack
💡
Cuando Android mata el proceso, toda la memoria RAM se borra: variables locales, objetos en el heap, ViewModels, todo. Pero el back stack de navegación sobrevive — Android lo serializa en disco y lo restaura al volver desde Recientes.

El problema: si el ID de la charla o los filtros estaban guardados solo en un MutableStateFlow normal (en memoria), se pierden. SavedStateHandle los serializa junto con el back stack.
¿QUÉ SOBREVIVE A LA MUERTE DEL PROCESO? ✅ Back stack (Android lo serializa automáticamente) ✅ Arguments de navegación (quedan en el back stack) ✅ SavedStateHandle (serializado junto al back stack) ❌ Variables de ViewModel (en memoria, se borra todo) ❌ MutableStateFlow normal (en memoria) ❌ Variables locales de Activity/Fragment FLUJO AL VOLVER DESDE RECIENTES: Android lee el back stack serializado │ ▼ Recrea la Activity de DETALLE (la que estaba en foco) │ ▼ El ViewModel de detalle recibe el charlaId desde SavedStateHandle │ ▼ Usuario toca "Volver" → Android sube al back stack │ ▼ Recrea la Activity de LISTA │ ▼ El ViewModel de lista recupera filtros desde SavedStateHandle (día = "Día 2", tema = "Datos")
a) Pantalla esperada al volver
✅ Pantalla esperada: el detalle de la misma charla
Android recrea la tarea desde el back stack serializado. La pantalla más reciente (detalle) se muestra primero. Al tocar Volver, el sistema navega hacia la pantalla anterior (lista) con los filtros de Día 2 / tema Datos, si estaban guardados correctamente.
b) Dónde guardar cada dato y por qué
DatoMecanismo correctoPor qué sobrevive
ID de la charla SavedStateHandle["charlaId"] en el ViewModel de detalle, o como argumento de navegación SavedStateHandle se serializa con el back stack. Sobrevive muerte del proceso Y rotación.
Filtro día savedStateHandle.getStateFlow("dia", "") en el ViewModel de lista Mismo mecanismo — se restaura automáticamente cuando Android recrea el ViewModel.
Filtro tema savedStateHandle.getStateFlow("tema", "") en el ViewModel de lista Igual que el filtro día.
Cómo identificar el bug y corregirlo
🔴 Código con bug — MutableStateFlow normal
Síntoma: al volver desde Recientes la lista aparece sin filtros o muestra el primer ítem en lugar del detalle correcto. Los filtros se reinician a "sin filtro".
// ❌ MAL — se pierde al morir el proceso class ListaViewModel : ViewModel() { private val _filtroDia = MutableStateFlow("") private val _filtroTema = MutableStateFlow("") } // ✅ BIEN — sobrevive a muerte del proceso class ListaViewModel(private val savedStateHandle: SavedStateHandle) : ViewModel() { val filtroDia = savedStateHandle.getStateFlow("dia", "") val filtroTema = savedStateHandle.getStateFlow("tema", "") fun setFiltroDia(dia: String) { savedStateHandle["dia"] = dia } fun setFiltroTema(tema: String) { savedStateHandle["tema"] = tema } }
5. Ciclo de vida de Android
🔄
Contexto del problema
Una Activity colecciona un Flow de Room con repeatOnLifecycle(STARTED). Un ViewModel descarga el programa en viewModelScope. La persona presiona Inicio → Activity pasa a STOPPED. El proceso sigue vivo.
🧠 Teoría: Estados del ciclo de vida
ESTADOS DEL CICLO DE VIDA DE UNA ACTIVITY: onCreate → onStart → onResume ↑ │ usuario interactúa (RESUMED) │ ↓ onStop ← onPause ← otra app al frente (STARTED → STOPPED) │ ↓ onDestroy ← usuario cierra app / Android mata proceso ESTADOS SIMPLIFICADOS: CREATED → existe pero no visible STARTED → visible (puede estar parcialmente cubierta) RESUMED → visible y en foco (usuario interactuando) STOPPED → en fondo, no visible (pantalla de inicio, otra app)
💡
repeatOnLifecycle(STARTED) = "coleccioná el Flow solo mientras la Activity es visible". Se cancela en STOPPED (fondo), se relanza en STARTED (vuelve al frente).

viewModelScope = scope del ViewModel, que vive mientras Android no destruya definitivamente la Activity (no cuando va al fondo, sino cuando el usuario la cierra o Android la elimina). Es independiente del ciclo de vida de la UI.
PRESIONA INICIO → Activity pasa a STOPPED: repeatOnLifecycle(STARTED) │ viewModelScope ─────────────────────────────│────────────────────────────── STARTED: coleccionando Flow │ Coroutine descargando... │ │ │ STOPPED: ✗ SE CANCELA │ STOPPED: sigue corriendo │ │ │ │ │ Descarga termina → StateFlow actualizado │ │ STARTED: ✓ SE RELANZA │ Ya terminó, StateFlow listo recibe último valor del Flow │ Activity recibe datos al instante
a) ¿Qué ocurre con cada componente?
ComponenteAl pasar a STOPPEDAl volver a STARTED
Colección del Flow
repeatOnLifecycle(STARTED)		 Se cancela. La Activity deja de recibir actualizaciones de Room. No consume recursos innecesarios en segundo plano. Se relanza automáticamente. Recibe el último valor emitido por el Flow de Room al instante.
Descarga del servidor
viewModelScope		 Continúa corriendo. viewModelScope es independiente de la UI — vive mientras el ViewModel exista. Ya terminó o sigue. El resultado estará en el StateFlow del ViewModel cuando la colección se relance.
✅
¿Por qué esta combinación es la correcta?
repeatOnLifecycle(STARTED) evita que la UI procese actualizaciones cuando no es visible (ahorra CPU/memoria). viewModelScope garantiza que la descarga no se cancele aunque el usuario vaya al home — así los datos llegan completos cuando vuelve. Son dos capas independientes que se complementan perfectamente.
6. Responsabilidades del patrón Repository
🏛
Contexto del problema
El catálogo observa charlas de Room. Al actualizar, Retrofit devuelve 12 charlas nuevas pero falla la escritura en Room antes de confirmar. La base todavía contiene la edición anterior.
🧠 Teoría: Patrón Repository y fuente de verdad única
💡
Single source of truth (fuente única de verdad) = Room es la única fuente de datos para la UI. La red no alimenta directamente al ViewModel — primero escribe en Room, y Room notifica al Flow.

Ventaja: la UI siempre muestra datos consistentes. Si la red falla, Room mantiene los datos anteriores. Si Room falla, la UI lo sabe a través de un estado de error.
FLUJO CORRECTO (patrón Repository): Usuario toca "Recargar" │ ▼ ViewModel llama a repository.sync() │ ▼ Repository llama a Retrofit (HTTP GET) │ ├── OK → Repository escribe en Room → Room emite Flow → ViewModel recibe │ └── Error (red o Room) → Repository devuelve Result.failure(e) │ ▼ ViewModel muestra banner de error Room NO cambió → UI sigue mostrando datos anteriores FLUJO INCORRECTO (antipatrón): ViewModel llama a Retrofit directamente │ ├── OK → ViewModel actualiza StateFlow con datos de red │ (UI inconsistente con Room, sin cache) │ └── Error → ViewModel muestra error (correcto accidentalmente)
a) ¿Qué lista debe observar el ViewModel?
✅ El ViewModel observa siempre Room — nunca Retrofit directamente
Flujo correcto: Retrofit → Repository escribe en Room → Room emite Flow → ViewModel recibe los datos actualizados automáticamente.

¿Por qué Room y no Retrofit? Room persiste los datos. Si el usuario mata la app y vuelve, los datos siguen ahí. Con Retrofit directo, al reabrir la app no habría datos hasta hacer otra request.
b) ¿Qué comunica el Repository cuando falla la escritura?
🔴 Fallo en Room.replaceAll() — ¿qué hace el Repository?
Si la escritura en Room falla, el Repository debe: (1) capturar la excepción, (2) devolver Result.failure(e), y (3) NO emitir los datos de Retrofit directamente al ViewModel. Room no cambió → la UI sigue mostrando los datos anteriores (edición vieja) con un banner de error.
// Repository — implementación correcta suspend fun syncPrograma(): Result<Unit> { return try { val remoto = api.getPrograma() // puede fallar db.charlaDao().replaceAll(remoto) // puede fallar Result.success(Unit) // ↑ si llega acá, Room tiene los datos nuevos y el Flow se actualiza solo } catch (e: CancellationException) { throw e // NUNCA atrapar cancelación } catch (e: Exception) { Result.failure(e) // ViewModel recibe el error, Room no cambió } } // ViewModel — observa Room, NO Retrofit val charlas: StateFlow<List<Charla>> = repository.getCharlas() .stateIn(viewModelScope, SharingStarted.WhileSubscribed(), emptyList()) fun sincronizar() { viewModelScope.launch { val result = repository.syncPrograma() if (result.isFailure) _uiState.value = UiState.Error("No se pudo actualizar") // si result.isSuccess, Room ya notificó el Flow automáticamente } }
7. Corrutinas y cancelación
⚡
Contexto del problema
Una función suspendida llama a Retrofit dentro de try–catch(Exception). El ViewModel cancela el Job mientras la función espera la respuesta. ¿Qué excepción intercepta ese catch? ¿Qué información se pierde?
🧠 Teoría: Cancelación cooperativa en Kotlin coroutines
💡
Cancelación cooperativa = las coroutines no se matan a la fuerza. Cuando cancelás un Job, Kotlin le lanza una CancellationException para que la coroutine pueda terminar limpiamente. Para que esto funcione, la coroutine no debe atrapar esa excepción.
JERARQUÍA DE EXCEPCIONES EN KOTLIN: Throwable └── Exception ← catch(e: Exception) atrapa ESTO ├── IOException ← error de red legítimo ├── HttpException ← error HTTP (4xx, 5xx) └── CancellationException ← ¡TAMBIÉN ES Exception! └── JobCancellationException CÓMO FUNCIONA LA CANCELACIÓN: job.cancel() │ ▼ Kotlin lanza CancellationException en el punto de suspensión (en el await() de la llamada a Retrofit) │ ├── Si la coroutine NO la atrapa → se propaga hacia arriba ✅ │ El scope la detecta → marca el Job como cancelado → libera recursos │ └── Si la coroutine la atrapa con catch(e: Exception) → BUG ❌ La función retorna "normalmente" con un resultado de error El scope cree que la coroutine terminó bien, no cancelada Puede seguir ocupando memoria o mostrando errores falsos
a) ¿Qué excepción intercepta el catch? ¿Qué se pierde?
🔴 El catch(e: Exception) intercepta CancellationException
CancellationException es subclase de Exception. Al atraparlo con catch(e: Exception) y retornar un resultado de error genérico:
(1) La cancelación no se propaga → el scope no sabe que el Job fue cancelado.
(2) La UI puede mostrar "Error de conexión" cuando en realidad no hubo ningún error de red — el ViewModel simplemente descartó el Job.
(3) Si el ViewModel ya no existe cuando esto ocurre, actualizar el StateFlow puede causar comportamiento indefinido.
// ❌ MALO — atrapa CancellationException silenciosamente suspend fun fetchData(): String { return try { api.getData() // si se cancela acá, lanza CancellationException } catch (e: Exception) { // ← atrapa CancellationException también _state.value = UiState.Error("Error de conexión") // bug silencioso "error" // retorna "normalmente", cancelación bloqueada } } // ✅ OPCIÓN 1 — re-lanzar CancellationException siempre suspend fun fetchData(): String { return try { api.getData() } catch (e: CancellationException) { throw e // SIEMPRE re-lanzar — deja que el scope la maneje } catch (e: Exception) { _state.value = UiState.Error(e.message ?: "Error desconocido") "error" } } // ✅ OPCIÓN 2 — más limpio: atrapar solo excepciones específicas suspend fun fetchData(): String { return try { api.getData() } catch (e: IOException) { // solo errores de red _state.value = UiState.Error("Sin conexión") "error" } catch (e: HttpException) { // solo errores HTTP _state.value = UiState.Error("Error del servidor: ${e.code()}") "error" } // CancellationException no está atrapada → se propaga correctamente }
⚠️
Regla de oro: CancellationException nunca debe ser silenciada. Si usás catch(e: Exception), siempre incluí catch(e: CancellationException) { throw e } primero. La opción más limpia es atrapar solo IOException / HttpException — así CancellationException se propaga automáticamente.

Unidad 1 — Activity Lifecycle
📱
P1 — Rotación de pantalla
Dificultad media · Lifecycle + ViewModel

Una Activity muestra el nombre de un usuario descargado de internet. Cuando el usuario rota el dispositivo, la app vuelve a hacer el pedido HTTP y muestra un spinner por 2 segundos.

⚠️
El jefe dice: "La red siempre va a ser rápida, no importa."
a) ¿Por qué la rotación dispara el fetch de nuevo? ▼
Al rotar, Android destruye y recrea la Activity (onDestroy → onCreate). Si el fetch se inicia en onCreate y el resultado se guarda en la Activity directamente (variable o campo), ese dato se pierde al destruirse. La Activity nueva arranca desde cero y vuelve a pedir los datos.
b) ¿Por qué el argumento del jefe es incorrecto? ▼
Incluso si la red es rápida, hacer un pedido innecesario consume datos móviles del usuario, aumenta la latencia perceptible y puede causar problemas si hay muchas rotaciones seguidas (race conditions de múltiples requests). Además, en entornos reales la red puede fallar o ser lenta.
c) ¿Cómo se corrige? Nombrá la clase que usarías y por qué sobrevive a la rotación. ▼
Se usa ViewModel. El ViewModel sobrevive a la rotación porque Android lo almacena en un ViewModelStore asociado al scope de la Activity, no a la instancia. Cuando la Activity se destruye por rotación, el ViewModelStore se retiene. La nueva Activity recibe el mismo ViewModel con el dato ya cargado.
class UserViewModel : ViewModel() { private val _user = MutableStateFlow<User?>(null) val user = _user.asStateFlow() init { viewModelScope.launch { _user.value = api.getUser() } } // init se llama UNA sola vez — no al rotar }
d) ¿El ViewModel sobrevive si el sistema mata el proceso? ¿Qué usarías en ese caso? ▼
No. El ViewModel NO sobrevive a la muerte del proceso (el sistema puede matar el proceso por falta de RAM cuando la app está en background). Para sobrevivir a eso se necesita SavedStateHandle (para datos pequeños, serializables) o Room/SharedPreferences (para datos persistentes). SavedStateHandle usa el mismo mecanismo de onSaveInstanceState.

P3 — Detectar antipatrones en ViewModel
Dificultad alta · MVVM + UDF

Analizá el siguiente código y encontrá todos los problemas:

class SearchActivity : AppCompatActivity() { private lateinit var viewModel: SearchViewModel override fun onCreate(savedInstanceState: Bundle?) { super.onCreate(savedInstanceState) viewModel = SearchViewModel() // ← (A) lifecycleScope.launch { viewModel.results.collect { items -> // ← (B) adapter.submitList(items) } } } fun onSearch(query: String) { viewModel.results.value = db.itemDao().search(query) // ← (C) } } class SearchViewModel : ViewModel() { val results = MutableStateFlow<List<Item>>(emptyList()) fun search(query: String) { // ← (D) — no se usa viewModelScope.launch(Dispatchers.Main) { // ← (E) results.value = db.itemDao().search(query) } } }
Respuesta: identificá y explicá cada bug marcado (A) a (E) ▼
(A) SearchViewModel() — no usar constructor directo
Hay que usar ViewModelProvider o by viewModels(). Con constructor directo, el ViewModel NO sobrevive a la rotación porque Android no lo puede gestionar.

(B) collect sin repeatOnLifecycle
En lifecycleScope.launch { ... collect { } }, la colección continúa incluso cuando la Activity está en background (onStop). Puede procesar eventos cuando la Activity no es visible. Lo correcto: repeatOnLifecycle(STARTED).

(C) lógica de negocio en la Activity + acceso a DB en hilo principal
db.itemDao().search() es una llamada síncrona a Room en el hilo principal → crash por NetworkOnMainThreadException (en Room equivale a un error de hilo). La lógica debería estar en el ViewModel.

(D) fun search() del ViewModel no se usa
La Activity ignora el método correcto del ViewModel y hace la query directamente. Violación de MVVM: la Activity no debería saber cómo se obtienen los datos.

(E) Dispatchers.Main para acceso a DB
Las queries a Room deben ejecutarse en Dispatchers.IO. Dispatchers.Main es el hilo de UI; hacer I/O ahí bloquea la interfaz.
💧
P4 — StateFlow vs Flow
Dificultad media · Reactive state
a) ¿Cuál es la diferencia principal entre Flow y StateFlow? ▼
Flow = frío (cold). No emite nada hasta que alguien lo colecta. Cada colector recibe una secuencia nueva. No tiene valor actual.
StateFlow = caliente (hot). Siempre tiene un valor actual. Cuando un nuevo collector se suscribe, recibe inmediatamente el último valor emitido. Ideal para representar estado de UI.
b) El ViewModel tiene private val _uiState = MutableStateFlow<UiState>(UiState.Loading). ¿Por qué se expone como StateFlow y no como MutableStateFlow? ▼
Encapsulamiento. Solo el ViewModel debe poder modificar el estado. Si la UI recibe un MutableStateFlow, podría llamar a .value = ... directamente desde la Activity/Composable, violando el principio de Unidirectional Data Flow (UDF): las acciones deben ir de la UI al ViewModel, nunca la UI modificar el estado directamente.
c) ¿Por qué se recomienda collectAsStateWithLifecycle() en Compose en lugar de collectAsState()? ▼
collectAsState() colecta el Flow mientras la Composable existe en la composición, sin importar si la Activity/Fragment está en background.
collectAsStateWithLifecycle() respeta el ciclo de vida: pausa la colección cuando el lifecycle está en STOPPED y la reanuda en STARTED. Esto ahorra batería y evita procesar actualizaciones cuando la UI no es visible.

@Entity(tableName = "notas") data class Nota( @PrimaryKey(autoGenerate = true) val id: Int = 0, val titulo: String, val cuerpo: String )
a) El cliente pide agregar una fecha de creación. Escribí la migración correcta (de versión 1 a 2). ▼
val MIGRATION_1_2 = object : Migration(1, 2) { override fun migrate(db: SupportSQLiteDatabase) { db.execSQL( "ALTER TABLE notas ADD COLUMN fechaCreacion INTEGER NOT NULL DEFAULT 0" ) // DEFAULT 0 → notas viejas quedan con epoch 0 (1970-01-01) // No se puede usar DEFAULT CURRENT_TIMESTAMP porque Room usa Long (ms) } } // En la DB: @Database(entities = [Nota::class], version = 2) abstract class AppDatabase : RoomDatabase() { abstract fun notaDao(): NotaDao companion object { fun buildDatabase(context: Context) = Room.databaseBuilder(context, AppDatabase::class.java, "app.db") .addMigrations(MIGRATION_1_2) // ← OBLIGATORIO .build() } }
b) ¿Por qué no se puede simplemente eliminar la tabla y recrearla? ▼
Porque los usuarios ya tienen datos en esa tabla. Si se hace DROP TABLE + CREATE TABLE, se pierden todas las notas existentes. La migración con ALTER TABLE ADD COLUMN agrega la columna nueva manteniendo todas las filas existentes intactas, con el valor por defecto definido.
c) ¿Cuál es la diferencia entre un DAO que retorna Flow<List<Nota>> y uno que retorna suspend fun getNota(): List<Nota>? ▼
Flow<List<Nota>> = Room emite automáticamente una nueva lista cada vez que la tabla cambia. El ViewModel recibe las actualizaciones sin necesidad de hacer queries adicionales. Ideal para listas que se muestran en la UI.

suspend fun getNota() = query one-shot. Se ejecuta una vez y devuelve el resultado. Si la tabla cambia después, el ViewModel no se entera automáticamente. Ideal para operaciones puntuales (verificar si existe algo antes de insertar).

P6 — SQL Injection
Dificultad media · Seguridad

Un usuario escribe en el campo de búsqueda: ' OR '1'='1

// Código vulnerable: fun buscarNotas(query: String): List<Nota> { return db.rawQuery("SELECT * FROM notas WHERE titulo LIKE '%$query%'", null) }
a) ¿Qué retorna esa query con la entrada del usuario? ¿Por qué es peligroso? ▼
La query queda: SELECT * FROM notas WHERE titulo LIKE '%' OR '1'='1%'
Como '1'='1' es siempre verdadero, retorna todas las notas, independientemente del título. Es peligroso porque permite acceder a datos que el usuario no debería ver. Con inputs más maliciosos se pueden ejecutar múltiples queries (; DROP TABLE notas --).
b) ¿Cómo se corrige en Room? ▼
Usando parámetros de binding (? o :param en Room). Room escapa automáticamente el valor:
@Dao interface NotaDao { @Query("SELECT * FROM notas WHERE titulo LIKE :busqueda") suspend fun buscarPorTitulo(busqueda: String): List<Nota> // Room convierte :busqueda en un ? y pasa el valor por separado // La entrada '%' OR '1'='1 queda como texto literal, no como SQL } // Uso: dao.buscarPorTitulo("%$query%") // el % es del LIKE, no es peligroso así
Unidad 4 — Red con Retrofit
🌐
P7 — Tres tipos de error en Retrofit
Dificultad alta · Error handling

Analizá el siguiente código:

suspend fun getProducto(id: Int): Producto { return api.getProducto(id) // retorna Producto (no Response<Producto>) }
a) El servidor devuelve HTTP 404. ¿Qué pasa? ¿Se lanza una excepción? ▼
Sí, se lanza HttpException. Cuando Retrofit retorna directamente el tipo (Producto en vez de Response<Producto>), Retrofit interpreta cualquier respuesta que no sea 2xx como un error y lanza HttpException con el código de estado.

Si en cambio retornara Response<Producto>, el 404 NO lanzaría excepción — habría que chequear response.isSuccessful.
b) El dispositivo no tiene internet. ¿Qué excepción se lanza? ▼
IOException (o su subclase UnknownHostException). Este tipo de error ocurre a nivel de conexión, antes de que llegue cualquier respuesta HTTP. No tiene código de estado porque nunca hubo comunicación con el servidor.
c) El servidor responde 200 pero el JSON tiene un campo diferente al esperado. ¿Qué pasa? ▼
Se lanza una excepción de conversión (ej: JsonDataException de Moshi, o JsonSyntaxException de Gson). El HTTP fue exitoso (200), pero la deserialización del body falló. Este es el tercer tipo de error.

Resumen de los 3 tipos:
1. Conexión → IOException (sin internet, timeout, host no resuelve)
2. HTTP → HttpException (4xx, 5xx — solo con tipo directo)
3. Conversión → JsonDataException / JsonSyntaxException (JSON inválido)
d) ¿Por qué se recomienda crear Retrofit como singleton y no crear una instancia nueva por request? ▼
Porque Retrofit.build() es costoso: crea el cliente HTTP (OkHttp), el pool de conexiones, los convertidores JSON, el DNS resolver, y registra los interceptors. Hacerlo por request desperdiciaría memoria y tiempo, y descartaría el pool de conexiones (que reutiliza TCP connections, mejorando la performance). El singleton se crea una vez y se reutiliza durante toda la vida de la app.
Unidad 5 — Sensores
📡
P8 — Tres problemas con sensores
Dificultad alta · Sensor lifecycle

Una app de fitness registra el acelerómetro con SENSOR_DELAY_FASTEST y registra el listener en onCreate:

override fun onCreate(...) { sensorManager.registerListener( this, accel, SensorManager.SENSOR_DELAY_FASTEST ) // ← Nunca se desregistra }
a) Identificá los tres problemas del código anterior ▼
1. Memory leak: el listener se registra pero nunca se desregistra. Cuando la Activity se destruye (rotación, usuario navega), el SensorManager sigue teniendo una referencia a la Activity. La Activity no puede ser garbage-collected → memory leak.

2. Alta frecuencia innecesaria: SENSOR_DELAY_FASTEST puede generar cientos de eventos por segundo. Para fitness, SENSOR_DELAY_NORMAL (200ms) es suficiente. El procesamiento de cada evento se hace en el hilo de UI, lo que puede causar jank y frames perdidos.

3. Sensor activo en background: si el usuario va a home, el sensor sigue corriendo. Consume batería sin que el usuario esté usando la app.
b) ¿En qué callbacks del lifecycle debería ir register/unregister y por qué? ▼
register en onResume — cuando la Activity está en primer plano y el usuario la está usando activamente.
unregister en onPause — cuando la Activity pierde el foco (dialog encima, va a home, navega a otra pantalla). El sensor se desactiva antes de que la Activity deje de ser visible.

Regla espejo: register y unregister deben estar en callbacks simétricos. onResume/onPause son el par correcto para sensores (no onCreate/onDestroy, que dejaría el sensor activo en background).
c) ¿Cómo se testea un sensor sin dispositivo físico? ▼
Se inyecta una dependencia falsa (fake/mock) que implementa la misma interfaz que el sensor real. En el test, se llama manualmente a onSensorChanged(fakeSensorEvent) con valores conocidos y se verifica que el ViewModel/Activity reacciona correctamente. En el emulador de Android también se puede simular valores de acelerómetro desde la pestaña "Virtual sensors" del Extended Controls.
Unidad 6 — Robótica e HMI
🤖
P9 — Patrón Gateway y diseño seguro
Dificultad media · Arquitectura robótica
a) En un sistema de control de robot, el ViewModel llama directamente a la librería ROS 2. ¿Cuál es el problema? ▼
El mismo problema que con Repository: el ViewModel conoce detalles de implementación (que se usa ROS 2, cómo se publican mensajes, el nombre del topic). Si se cambia de ROS 2 a MQTT, habría que modificar el ViewModel.

La solución es el patrón Gateway: una interfaz entre el ViewModel y la tecnología de comunicación. El ViewModel llama a robotGateway.mover(velocidad) sin saber si internamente usa ROS 2, MQTT o WebSocket.
b) ¿Qué significa "enviar no es ejecutar"? ¿Por qué es importante en robótica? ▼
Enviar un comando al robot (publicar un mensaje ROS 2) no garantiza que el robot lo ejecute. El mensaje puede perderse (red poco confiable), llegar tarde, o el robot puede estar en un estado donde no puede ejecutarlo.

Por eso el diseño seguro incluye confirmación asíncrona: el robot envía un mensaje de vuelta confirmando que ejecutó la acción, o la app implementa un timeout que asume fallo si no hay confirmación. En sistemas de seguridad (robots cerca de personas) esto es crítico.
c) ¿Cuáles son las tres formas de comunicación en ROS 2 y cuándo se usa cada una? ▼
Topics (pub/sub): streams continuos de datos (posición del robot, lecturas de sensores). Many-to-many. Sin confirmación de recepción.

Services (request/response): operaciones discretas con respuesta (encender un gripper, consultar el estado de la batería). Sincrónico en términos de lógica (espera respuesta).

Actions: tareas largas con feedback progresivo y posibilidad de cancelar (navegar a un punto, que puede tardar minutos). Incluye goal → feedback periódico → result final.
Unidad 7 — Lectura de repo desconocido (tipo examen)
🔍
P10 — Diagnóstico en código desconocido
Dificultad muy alta · Sintoma → Concepto → Corrección

Alguien te da acceso a un repo de Android que nunca viste. La app tiene estos síntomas. Para cada uno: nombrá el concepto, explicá por qué ocurre y cómo lo corregirías.

Síntoma A: "Al rotar el dispositivo, la app hace un request HTTP nuevo y el spinner aparece por 2 segundos cada vez" ▼
Concepto: datos guardados en la Activity (o iniciados en onCreate sin ViewModel)
Por qué: la rotación destruye y recrea la Activity → el fetch se reinicia
Corrección: mover el fetch al init del ViewModel. El ViewModel sobrevive a la rotación.
Síntoma B: "La app consume el 100% de la CPU aunque el usuario no esté mirando la pantalla (en background)" ▼
Concepto: sensor listener no desregistrado (memory/battery leak) o coroutine sin cancelar en background
Por qué: el listener/coroutine sigue activo aunque la Activity/Fragment esté en STOPPED
Corrección: para sensores → mover unregister a onPause. Para coroutines → usar repeatOnLifecycle(STARTED) o viewModelScope que cancela al limpiar el ViewModel.
Síntoma C: "La app crashea con ANR (Application Not Responding) cuando tiene mala conexión" ▼
Concepto: operación de red o I/O en el hilo principal
Por qué: el hilo de UI se bloquea esperando la respuesta de red. Android detecta que el hilo principal no procesa eventos por más de 5 segundos → ANR
Corrección: mover la operación a Dispatchers.IO usando withContext(Dispatchers.IO) { ... } o marcando la función con suspend.
Síntoma D: "Los datos persisten en la app aunque el usuario los haya borrado. Se actualiza solo si se cierra y reabre la app." ▼
Concepto: el ViewModel observa el resultado de un fetch one-shot (suspend fun) en vez de observar el Flow de Room
Por qué: si el ViewModel tiene val items = repository.getItems() donde getItems() es una suspend fun, solo carga una vez. Los cambios en Room (borrados) no se notifican.
Corrección: el DAO debe retornar Flow<List<Item>>. Room automáticamente emite la lista actualizada cada vez que hay un INSERT, UPDATE o DELETE.
